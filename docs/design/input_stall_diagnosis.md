# 「Windows 卡住 / 游戏正常」输入链排查路径

> AGENTS.md 参考资料分册。本文件是**判读顺序**，不是新机制：机制细节见 [key_designs_base.md#键盘钩子健康探针](key_designs_base.md#键盘钩子健康探针) 与 [key_designs_hotkey.md](key_designs_hotkey.md)。
> 记录目的：这条现象每次都被重新怀疑一遍 AFA 主线程，而"主线程停顿会不会冻结全局输入"这个假说早已有结论（见[第 5 节](#5-已证伪的假说不要重复验证)）。

## 1. 现象与它已经排除掉的东西

**现象**：整个 Windows 的键鼠输入一起变卡/无响应（点开始菜单、切窗口、打字都卡），但**游戏本身运行正常**（画面在动、帧率正常、游戏内鼠标视角正常）。

这条组合本身就是最重要的证据：**输入在被"交给谁"的环节卡住了，而不是机器在算不动**。

- 如果是整机资源问题（CPU/内存/磁盘打满），游戏会一起掉帧——"游戏正常"直接排除它。
- 如果是 AFA 停止响应，那么受影响的应当只有 AFA 的热键动作；**系统级输入（开始菜单、任务栏、其它程序）本来就必须照常工作**——原因见第 5 节。
- 剩下的解释只有一个方向：**输入事件在到达前台窗口之前，被链上的某个环节延迟或吞掉了**。

## 2. 判读顺序（不要跳步）

### 第 1 步：读系统低级钩子超时值

Windows 允许每个低级钩子（`WH_KEYBOARD_LL` / `WH_MOUSE_LL`）的处理有时间上限；超时的钩子会被系统**静默忽略**，累计多次后该钩子进程被移出链。这个上限就是排查的第一个数：

```
reg query "HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Windows" /v LowLevelHooksTimeout
```

- 键不存在 ⇒ 用系统默认值（本机实测：该键**不存在**）。该键存在但数值很小时，任何钩子持有者的短暂停顿都会被放大成"输入丢失"。
- AFA 侧相关预算：`main.ahk` 的 `#HotIfTimeout 100`（AHK 默认 1000ms，比系统红线宽得多，故收紧）；动作层最长不可中断窗口是失焦悬停激活的 `HotkeyService.ActivateTimeoutMs`(200ms)。

判读时注意：**这个键缺失不等于没有超时**，只等于用默认值。

### 第 2 步：看外设/宏类软件进程

链上每一个"能改键、能录宏、能注入"的软件都可能装一个低级钩子；两个以上这类软件同时常驻时，谁先谁后由安装/启动顺序决定，行为可以完全不符合直觉（例如某软件只在特定游戏里启用配置，或钩子只在它自己前台时才转发）。

**AFA 已经把这个事实写进诊断包**：`diagnostics.txt` 里的 `RunningProcessCount` 与 `RunningProcesses` —— 导出那一刻的**完整进程名列表**（按字母排序、只列名字，不含 PID/路径/命令行）。取列表用系统自带的 `tasklist`（见 `core/diagnostics/log_exporter.ahk`）。

这些行**只记录事实、不下结论**——进程在跑不等于它是原因，没跑也不能排除（宏功能可能只存在于驱动/内核层，甚至没有常驻进程）。

> 复现要求：**要在故障发生的同一时间窗口内取证**。事后才去翻进程列表，看到的往往是用户已经把那个软件关掉了的状态。

### 第 3 步：看钩子链本身

要知道"到底哪些进程装了钩子、顺序如何"，用 Process Explorer：

1. 以管理员运行 `procexp64.exe`；
2. `Ctrl+D` 或菜单 `View → Lower Pane`，下方选 `DLLs`；
3. 在任意窗口进程里找 `..._LL` 相关项：`WH_KEYBOARD_LL`、`WH_MOUSE_LL` 会以 `Hook` 任务的形式列出持有者（Process Explorer 的 `View → Show Lower Pane` + 列 `Hook` 亦可）。

判读要点：
- 链上出现**陌生进程**，或者出现了第 2 步清单里的软件 → 优先怀疑它。
- 链上项目数远超预期（每个输入类软件/助手/截图工具/录屏/远程控制都可能挂一个）→ 延迟会被累加。
- **AFA 自己的 AHK 进程在链上是正常的**——AFA 的热键大量使用低级钩子（见 `key_designs_hotkey.md` 的"热路径预算"）。链上出现 AFA 不构成故障证据。

### 第 4 步：把 AFA 与"原始输入"对照

最省事的判别实验：**同时**开一个与 AFA 完全无关的裸输入观察器（另一个 AHK 小脚本/在线键盘测试页/键盘 LED 测试），让两边同时收键：

- 裸观察器**也收不到** → 问题在 AFA 之外（前置钩子/系统），继续第 2、3 步。
- 裸观察器**收得到、只有 AFA 的热键不响应** → 才是 AFA 内部问题，看第 6 节。

### 第 5 步：最后才怀疑 AFA 自身

AFA 提供的证据链（都在日志里，配合 `HookHealth` 快照读）：

| 观察点 | 含义 |
|---|---|
| `[WARN] [HookHealth] 物理按下未触发热键` | 探针用**不依赖钩子**的 `GetAsyncKeyState` 采到物理按下，但宽限期内没有任何热键回调 |
| 快照 `idle=…, idleKbd=…, idlePhys=…` **三值恒等** | 钩子确已不再被系统调用（`A_TimeIdleKeyboard`/`A_TimeIdlePhysical` 退化为 `A_TimeIdle`）；三值有差异说明钩子仍在正常区分键盘与鼠标输入 |
| 快照 `ctxEval=max/avg/n` | 单次 `HotIf` 求值耗时（**本快照里唯一的耗时项，也是唯一可验证的一项**）——求值就在钩子判定路径上，这个数大＝主线程在判定路径上停顿 |
| 快照 `recover=` | 累计自愈次数。反复增长说明冲突在持续，**不要**靠继续重装钩子解决 |
| `[WARN] [HookHealth] 物理按下未触发热键` 与"切换窗口"同时出现 | 属**假阳性**，已在结算时复核判定前提修掉（见下） |
| `[WARN] [HookHealth] 钩子自愈：…抢占优先级` | 每次强制重装都会改变钩子链优先级顺序，见第 6 节 |
| `[INFO] [HotkeyActions] <动作> 阶段N/M …` | 动作执行到哪一步。卡死时最后一条阶段日志即断点（阶段日志覆盖全部多阶段动作，500ms 节流） |
| `[WARN] [KeyForward] 等待物理松开已 30s` | 动作卡在 `PureKeyWait`：若不是用户按着不放，就是钩子已失效导致的永久挂起（对照 `depth`/`inflight`） |

判读顺序：先看**钩子是否还被调用**（三值恒等 + miss），再看**AFA 内部耗时**（ctxEval），两者不要混着读。

**"这次按下是否已被回调消费"的判据，必须以「上次观测到抬起」为基准**：

- 一次回调属于"新的一次按下"，当且仅当**它发生在观测到该键抬起之后**。若某键刚发生过回调、而我们**还没见过它抬起**，那么新的按下沿就是那次回调的来源，不该再建档——否则 3 秒宽限期后无人清理，必然误报"未触发热键"。
- 为什么不能用"回调是否晚于上次按下沿"：**按下与回调几乎同时发生**（AHK 钩子在输入到达时同步执行回调），而探针 100ms 才采一次样。快速点按（按下-松开远短于采样周期）会整段跳过"抬起"，使该判据给出相反结论——表现为每次点按都误报一条 `物理按下未触发热键`（自证计数上可见"建档持续增长而 cleared 恒为 0"）。
- 用"上次观测到抬起"当基准后与采样快慢无关。漏掉抬起只会导致"这次按下不建档"（不误报），不会削弱"钩子真失效"的检测：那种情况下回调计数长期不增长，下一次可辨识的按下仍会建档并如实报 miss。
- 快照里的 `probe=[键(arm=…,raceSkip=…,cleared=…,miss=…,discard=…,watchDrop=…)]` 就是这条判据的自证：正常时 `arm ≈ cleared + miss + discard + watchDrop`；`cleared` 长期为 0 或 `miss` 持续增长即为异常。

**前提必须在"建档时"和"结算时"都成立，任一失效就作废**（两条已实现 + 一条即时通道）：

| 前提 | 失效场景 | 处理 |
|---|---|---|
| 该键仍是当前注册的热键 | 用快捷键禁用热键 / 切标签页重建分组 | **即时刷新**监视表（`HotkeyService._NotifyWatchKeysChanged()` 调 `HookHealth.RefreshWatchKeysNow()`），并在结算时复核 `_IsWatchedKey()`（记为 `watchDrop`） |
| 前台仍是建档时那个窗口 | 按下后切走窗口（热键按设计不再触发） | 结算时比对建档留档的 `fgHwnd`，变了就作废（记为 `discard`） |
| 鼠标键的光标仍在游戏客户区 | 按下后把光标移出游戏窗口 | 结算时复核 `IsMouseInClient()`，不成立就作废（记为 `discard`） |

> 为什么"禁用热键"必须即时通知探针：定时刷新间隔是 5s，而 `HotkeyOff()`/`EnableByTab()` 会**立刻**清空 `ActiveHotkeys`。这个空窗里探针仍盯着已注销的键，按下它 → 建档但永远没有回调（**本就不该有**）→ 宽限期后误报"物理按下未触发热键"。**复现**：按一次某键并松开 → 3 秒内禁用热键 → 5 秒内再按同一键。

**关于耗时指标的一条重要边界**：

- **只有 `ctxEval` 保留**。它是脚本自己函数的求值耗时，用 QPC 前后夹逼，单元测试可直接断言；而且它与"钩子被系统摘除"直接相关（求值超时会被系统记一次超时）。阈值 50ms，超标落 WARN。
- **曾经还有一项 `inToAction`（首次求值 → 动作线程开始），已整项移除**。它在生产上连报过多次"输入交付 3.9s"假延迟，根因是区间起点会被 key repeat 重复登记、以及清理动作一度被"游戏前台"门挡住；而**脚本侧无法独立验证该区间的真实性**——同一份数据里既有真排队也有残留，读的人无法分辨。判断标准是：测不准的指标一律不留，避免污染判读。
- **"输入在到达本进程之前被拖了多久"脚本侧根本无法打点**：AHK 不向脚本暴露低级钩子过程入口。这一段只能靠 `miss` 计数与 `idle` 三值间接判断（钩子是否还被系统调用）。
- 因此判读顺序是：**先看 miss + idle 三值（钩子还活着吗）→ 再看 ctxEval（判定路径被拖了吗）→ 两者都正常却"按键没反应"，问题多半在 AFA 之外**（回到第 2、3 步查前置钩子）。

## 3. 为什么不给动作注入序列加阶段日志（已否决，勿重走）

曾经在 `hotkey_actions.ahk` 的每个动作里逐阶段打 INFO（进入 / 已取光标 / 已 BlockInput / 已注入 / 已还原），目的是"卡死时能看出停在哪一步"。**该方案已整体回滚**，原因是一条硬约束：

> **在 `Send "{XXX Down}"` 与 `Send "{XXX Up}"` 之间插入任何 I/O，都会改变游戏看到的按键语义。**

游戏 PC 端**按帧开头轮询**按键状态（见 [key_designs_hotkey.md](key_designs_hotkey.md#明日方舟-pc-端按键识别帧开头状态轮询)）。日志写盘是文件 I/O，单次可能耗 10~30ms；把它插在 Down/Up 之间，会把这段间隙从"远小于一帧"拉长到**跨帧**：

- 两次 Send 落在同一帧内 → 游戏根本没看到这个键（等效于没按）；
- 被拉长到跨帧 → 游戏在帧头轮询到了按下。

于是同一个操作会**时灵时不灵**：把「返回上级菜单」绑到右键并勾选"使用返回上级菜单放弃行动"后，按右键时而返回、时而放弃行动。原因就是阶段日志正好插在 `ESC Down` 与 `ESC Up` 之间，把这段从 <1ms 拉到 60~80ms。

**结论与替代做法**：

- 动作内部**只在入口/出口各留一条**原有 DEBUG，不逐阶段打点；需要定位卡死位置时靠**时序**（最后一条日志的时刻 + `HookHealth` 快照的 `depth`/`inflight`）而不是靠阶段序号。
- 真正危险的"卡在等待"已有覆盖：`PureKeyWait` 的 3s/30s DEBUG 与 30s WARN（它只在**等待期间**打点，不插在 Send 序列里）。
- 若将来确实需要更细的时序观测：用内存计数 + 事后一次性导出（快照/诊断包），**不要**在按键序列中间做 I/O。

## 3. 什么时候导出诊断包

只要出现"输入卡住"就必须导出，越接近故障时刻越有价值：

- 诊断包里的日志是**逐条时间戳**的，故障时间窗内的 `HookHealth` WARN、`HotkeyActions` 阶段日志、`KeyForward` 等待物理松开日志会连成一条链；
- 诊断包同时带上了第 2 步的环境事实（外设/宏进程），省掉"事后靠记忆回忆当时装了什么"。

导出口径与脱敏规则见 `core/diagnostics/log_exporter.ahk` 与 [key_designs_base.md](key_designs_base.md)。

## 4. 为什么"日志里什么都没有"其实也是证据

如果一次卡顿之后，日志里既没有 `HookHealth` 的 miss/心跳异常，也没有 `HotkeyActions` 阶段日志、没有 `inToAction` 峰值，那说明：**在你按的那些键上，AFA 从头到尾没被调用过。**

结合第 1 节，这正是"输入在到达 AFA 之前就被拦住/拖住"的形态——此时故障发生在第 2、3 步的范围内，而系统钩子超时是**累计式**的（可能已经发生过 10 次超时但还没到摘除阈值），所以 AFA 侧看不到任何异常也不矛盾。

## 5. 已证伪的假说（不要重复验证）

> **假说**：AFA 主线程停顿（忙等 / 不可中断段）会先把整机输入冻住，然后才轮到 AFA 自己。
>
> **结论：不成立，别再重复验证。** 两个层面都不成立：

1. **实现层面**：AFA 的停顿只发生在"求值热键条件"与"执行动作"这两段自己的线程里。判断"要不要触发"确实占据输入路径（`HotIf` 求值在钩子判定路径上，所以它慢会导致钩子被系统判超时、进而**摘掉 AFA 自己的钩子**），但**它只影响 AFA 自己注册的热键**；被摘掉之后 AFA 热键失效、输入透传，**系统的输入流照常**。
2. **实测层面**：本项目与用户侧的历史复现都出现过"整机输入冻结而游戏正常"的场景，恢复方式与 AFA 侧任何日志/自愈动作无关，而是外设/宏软件的配置或进程状态变化。

因此这条现象**不该**再被当作"验证 AFA 主线程停顿"的入口：真正会冻结整机输入的是**链上其它进程的低级钩子不返回**（系统必须等钩子返回才继续分发），以及驱动层问题——都不在 AFA 进程内，当然也不会触发 AFA 的任何自愈。

> 需要注意的另一个方向（**属于 AFA，但表现不同**）：AFA 的键盘钩子被系统摘除后，`KeyWait` 等依赖**物理键态**的等待会永久挂起，动作线程堆满 `#MaxThreads`(默认 10) 后所有热键都无法启动。这条在日志里**看得见**（`[DEBUG] [KeyForward] 等待物理松开已 Ns` + 快照 `depth=max 10`），与"整机输入冻结"是两回事，不要混为一谈。

## 6. 自愈的代价：为什么阈值抬高、冷却拉长

`HookHealth._OnSuspected()` 用 `InstallKeybdHook(true, true)` 自愈。官方文档（`docs/ahk_docs/lib/InstallKeybdHook.htm`）对该参数的原话是：

> If true and Install is true, the hook is uninstalled and reinstalled. This has the effect of **giving it precedence over any hooks previously installed by other processes**. If the system has stopped calling the hook due to an unresponsive program, reinstalling the hook might get it working again.

也就是说自愈是**带副作用的**：它对"钩子被系统摘除"有效，但对"输入被前置钩子吞掉"这类冲突，等于**主动去抢别人的钩子优先级**——冲突可能因此更乱（对方软件也可能据此重新注册，形成来回抢占）。

故当前策略：

- 连续未命中阈值 `MissThreshold` = 5（原 3）；
- 自愈冷却 `RecoverCooldownMs` = 30000ms（原 5000ms）；
- 每次自愈落一条 WARN，明确写出"已强制重装并抢占优先级"，并带累计次数；
- 快照输出 `recover=` 累计自愈次数。

**判读**：`recover` 持续增长 ⇒ 停止把自愈当作解决办法，转而排查第 2、3 步的前置钩子；把 AFA 的钩子链优先级被谁抢、以及每次自愈的时间点与用户操作时间线对照。
