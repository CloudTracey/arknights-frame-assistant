# 测试清单：`compiled_web_engine`

> 对应更改：让**编译版也能使用 web 引擎**。`FileExtractor` 用 `FileInstall` 嵌入并提取页面资源与 **x64** `WebView2Loader.dll` 到 `%AppData%\ArknightsFrameAssistant\PC\web\`；`WebHost` 的页面目录与加载器路径改从提取目录取，预检删掉 `A_IsCompiled` 分支（源码与编译版走同一路径）。
> 附带重构：文件 SHA-256 抽成 `base/file_integrity.ahk`（`FileIntegrity.Sha256`），供 `downloader.ahk` 的下载校验与加载器校验共用，删除 `Downloader._GetFileSha256`。
> 不包含：web 模式的"切回经典界面"出口（**发版前置条件**，前端落地时再补）。

- [ ] **说明**：**负路径（哈希不符）无法自然构造**——`ExpectedHash` 来自发布端数据，本地改不了。这部分只能静态审阅（`FileIntegrity.Sha256` 与原 `_GetFileSha256` 逐行一致，且 1MB 分块、`finally` 释放句柄的行为未变）。若连正常下载也无法进行，请标注为"仅静态审阅"。

> 静态审阅结论：`FileIntegrity.Sha256` 的 CryptoAPI 调用序列、1MB 分块循环、三层 `finally` 释放（hash → provider → file）与失败返回空串的语义均与原 `Downloader._GetFileSha256` 逐行一致；调用点仅把 `this._GetFileSha256(...)` 换成 `FileIntegrity.Sha256(...)`，其后的 `actualHash = "" || StrLower(actualHash) != StrLower(ExpectedHash)` 判据未动——即"校验失败则删文件并中止更新"的行为不变。
> 残留风险：低（纯搬移 + 改调用点，无逻辑变更），但**未经一次真实下载验证**。

## 问题反馈

### 问题1：测试记录曾把编译版会话误标为「源码版回归」通过
- [x] 已解决（记录已纠正，源码版回归改为"未运行验证"）

**现象**：验收过程中先按时间把 03:04:02 / 03:05:56 两个会话标为"源码版回归通过"，随后核对日志的 `管理员进程启动，脚本=<A_ScriptName>` 字段才发现它们是 `main.exe`（编译版）。
**根因**：判断运行方式时凭推测而非证据。日志里本就有判别字段（`.ahk` = 源码运行，`.exe` = 编译版），一开始没用上。
**处置**：逐个会话核对脚本名——近 30 个会话为 10 个 `main.exe` + 3 个 `main.ahk`，且那 3 个源码会话全部跑在 `classic`；据此把"源码版回归"改回未勾并写明纠正过程与影响评估（统一路径后 `WebHost` 已无 `A_IsCompiled` 分支，残余风险低）。
**教训**：涉及"编译版/源码版"的验收项，结论必须附 `脚本=` 字段作证据，不能靠推断。
