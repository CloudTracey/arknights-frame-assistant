# 测试清单：过帧时序保护与 USleep 超时诊断

> 对应更改：为过帧等时序敏感动作的 Send/Touch 序列加 `Critical` 保护（防止 LevelDetector 定时器中断导致过帧时序波动），并在 `USleep` 到期时记录超出 target 的时长（毫秒）便于诊断。

## 单元测试

### 功能点：USleep 超时诊断日志

- [x] **操作**：启动 AFA，打开设置窗口，在「其他设置 → 日志」中勾选「启用调试模式」并应用
- [x] **预期**：开启调试模式后，日志中开始记录 DEBUG 级别日志（或实时控制台打开）
- [x] **操作**：进入游戏关卡，执行 16ms 过帧操作若干次
- [x] **预期**：日志中出现格式为 `USleep 超时 X.Xms，delay=16ms` 的记录（`Logger.Debug` 级别，component 为 `USleep`）
- [x] **操作**：观察过帧时日志中的 `USleep 超时` 数值
- [x] **预期**：正常（无中断）时 overshoot 通常 < 1ms，不会触发日志记录；触发记录的值以毫秒为单位，可反映实际超出量

### 功能点：Critical 保护不改变动作本身

- [x] **操作**：游戏外（不在关卡界面）按下任意已绑定的过帧热键（16/33/166ms）
- [x] **预期**：与改动前一致，被关卡守卫拦截、原键透传，日志记录「被关卡检测拦截（不在关卡界面）」，动作不执行

## 集成测试

### 流程：16ms 过帧精度验证（核心）

> 涉及模块：`hotkey_actions`、`level_detector`、`game_monitor`

- [x] **前置**：已开启调试模式；进入任意关卡，准备一个可稳定过帧的场景
- [x] **操作**：连续执行 16ms 过帧 20 次以上，同时观察游戏内实际推进帧数
- [x] **预期**：改动后「间隔太短不过帧」「间隔太长一次过两帧」现象较改动前明显减少（若未明显改善，记录现象以便进一步定位）
- [x] **操作**：过帧过程中观察日志中 `USleep 超时` 的记录
- [x] **预期**：大部分过帧不产生 `USleep 超时` 记录；偶发的记录值应在数 ms 以内（非十几 ms 到几十 ms 的异常值）
- [x] **操作**：记录出现「一次过两帧」或「不过帧」时，日志中 `USleep 超时` 的数值
- [x] **预期**：若「一次过两帧」伴随 `USleep 超时 5~50ms`，可确认时序被外部中断拉长；`Critical` 已抑制该中断源

> **验证结论（对照实验，2026-08-11）**：加 `Critical` 后无任何 `USleep 超时` 记录，过帧改善程度明显；临时注释掉 `Critical` 复测，出现大量十几 ms 的 `USleep 超时`。确认 root cause 为 `LevelDetector` 定时器中断过帧序列，`Critical` 修复有效。

### 流程：33ms / 166ms 过帧验证

- [x] **预期**：两种过帧均稳定，不出现明显的间隔波动或跳帧

### 流程：暂停/倍速/一键/暂停技能撤退等时序动作验证

> 涉及模块：`hotkey_actions`、`touch_injection`

- [x] **预期**：各动作均正常执行，未出现动作失效、时序错乱或卡顿（这些动作同样被加上了 Critical，需确认无回归）
