## 问题反馈

### 问题1：清除失效路径后，只读总览框没有立即更新
- **现象**：保存时选「是」清除失效记录后，保存流程本身正确；但「已识别区服路径」只读框仍显示那条已失效的路径，必须点「取消」、关闭窗口或重启 AFA 后才更新。
- **原因**：`GuiManager._OnSettingsSaved` / `_OnSettingsApplied` 的普通分支从不刷新该只读框；只有取消路径发布的 `SettingsViewRefreshRequested` 会调用 `_RefreshServerPathsText()`，所以只有在取消/重开窗口时才看到更新。
- **修复**：两个事件处理器的普通分支各补一次 `_RefreshServerPathsText()`（未新增事件，未改事件契约）。
- [x] 已解决
- [x] 回归验证通过（见「功能：问题1 修复后的回归」）

### 问题2：「存在的非 Arknights.exe 文件」被误判为有效游戏路径
- **现象**：把「随AFA启动游戏路径」改成 `C:\Windows\System32\notepad.exe` → 保存**成功**，「路径不正确」校验从不触发。
- **原因**（既有缺陷，非本次改动引入，但被本次新增回归项暴露）：`ServerProfile.FromExePath` 在文件名不是 `Arknights.exe` 时，会把传入路径当作**目录**继续识别；随后第 3 步“注册表兜底”只检查本机某服注册表根下是否存在 `KEYBOARD_SETTING_V*`，**与传入路径无关**。因此只要本机装过任意区服，任何存在的文件都会被判成该区服，校验被完全绕过。
- **修复**（最终）：`FromExePath` 只接受名为 `Arknights.exe` 的文件路径，其余（含目录、驱动器根、尾反斜杠目录、其他文件）一律返回 `Unknown`；需要传游戏目录的调用方改用 `FromGameDir`（本次一并让它 `RTrim` 掉尾反斜杠）。
  > 演进：首版修复只做了"文件名不匹配时先判目录"，PR #363 评审指出该写法仍接受目录——已核实 `C:\Windows\System32`、`E:\`、含 `Arknights Game` 特征的目录都会被注册表/目录特征兜底判成已装区服，故改为完全不容忍目录形式（见问题5）。
- **附带确认**：“存在且名为 Arknights.exe 但不在游戏目录”的文件**仍然接受**（自定义安装位置），这是刻意保留的行为。
- [x] 已解决
- [x] 回归验证通过（见「功能：问题2 修复后的回归」）

### 问题3：“存在但不是 Arknights.exe”的路径，识别按钮不会清（交互不对称）
- **现象**（评审中发现，非踩坑报告）：保存校验会拒这类路径，但点「识别游戏路径」不会清除它，用户点识别也脱不了困；原设定只判 `FileExist`。
- **修复**：`GameLauncher._CleanUpGamePaths`（原 `_ClearMissingGamePaths`）的判定与保存校验对齐——`FileExist` 失败 → 「路径不存在」；`FromExePath` 返回 `Unknown` → 「路径不正确」；两者都清。被清项在失败提示里带原因前缀，日志记录原因。
- **刻意保留**：判定用与保存校验同一个 `FromExePath`，而不是单纯比较文件名——否则“重命名过但仍能经 app.info/注册表识别”的合法安装目录会被误删（回归项见「功能：问题2 修复后的回归」末条）。
- [x] 已解决
- [x] 回归验证通过（见「追加测试：识别按钮同时清理…」）

### 问题4：「随AFA启动游戏路径」输入框在清除后不即时更新
- **现象**：保存时选「是」清除失效路径后，**只读总览**已即时刷新，但上面的「随AFA启动游戏路径」输入框仍显示那条已清除的路径，必须取消设置或重启 AFA 才更新。
- **原因**：该输入框只由事件回写——`GamePathNormalized` 仅在「随明日方舟自动启动AFA」开启时经 `_ApplyGameAutoStart` 发布，`GamePathDetected` 只在识别流程发布；保存时的内存清理不走这两个事件，因此界面与实际配置不一致。
- **修复**：新增 `GuiManager._RefreshGamePathControls()`（同步 `GamePath` 输入框 + 已识别区服路径总览），在 `_OnSettingsSaved`、`_OnSettingsApplied`、`_OnSettingsViewRefreshRequested` 三处调用，取代原先只刷总览的 `_RefreshServerPathsText()`。未新增事件（`GamePathNormalized`/`GamePathDetected` 已各有唯一发布者）。
- [x] 已解决
- [x] 回归验证通过（见「功能：问题4 修复后的回归」）

### 问题5：PR #363 评审的两条 blocking 意见（目录未被拒 + 清理提前改内存）
- **评审意见1（目录仍可被接受）**：成立。用**真实修复前代码**（`git show 001f2c7^:src/lib/base/server_profile.ahk`，md5 校验后实测）确认：`C:\Windows\System32`、`E:\`、尾反斜杠目录全部判为 `CN / registry`，**保存校验放行**；与"配置项必须是 Arknights.exe 文件"的契约矛盾。
  > 实测补充（用户复验时提出"旧版也能拒绝目录"，回溯后定位）：测试时开着「随明日方舟自动启动AFA」，目录是被 `GameAutoStartManager.ValidateGamePath` 以「无法启用随游戏自动启动」拦下的——即**保存校验放行、由下一道自启校验兜住**，弹窗标题与「路径不正确」不同。这恰好印证了评审说的"校验不对称"；关闭自启时目录可直接存入配置，之后启动游戏才报「游戏文件不存在」。
- **评审意见2（清理在保存中止时已改内存）**：成立。首版在弹窗确认后立即 `SetImportant(key, "")`，若后续校验/外部设置/落盘失败，保存中止但内存里的记录已消失——最隐蔽的后果是用户随后点「取消」（`LoadFromIni`）会把刚确认删除的记录又恢复回来。
- **修复**：①`FromExePath` 完全不容忍目录形式（目录交给 `FromGameDir` 处理），`_CleanUpGamePaths` 同步把目录判为「路径不正确」；②保存流程只记录用户确认的清理意图，真正清内存推迟到全部校验与外部设置之后、`SaveAllToIni` 之前（抽出 `_ClearConfirmedPaths()`）。
- **评审中不成立/需修正的部分**：评审称"新增回归测试的预期是 `C:\Games\` 应被拒绝"——清单里当时并没有这条显式预期（只有"目录 → 路径不正确"这一条，来自 `C:\Windows\System32`）；该契约来自 `ValidateGamePath` 与既有清单条目，现已补充针对目录的显式回归项。另评审把"保存流程的清理"与"可能永久丢记录"关联，实际上永久落盘只发生在识别按钮路径（本就有 `FileExist`/`FromExePath` 双重判定且可重新识别），保存路径的清理首版就已只改内存。
- [x] 已解决
- [x] 回归验证通过（见「追加测试：评审修复…」）

### 问题6：清完失效路径后开着自启，保存被“游戏路径不存在或不是文件”二次挡住（点不动）
- **现象**：删掉已识别的游戏 → 保存/应用 → 弹「路径不存在」→ 选「是」→ 又弹「无法启用随游戏自动启动：游戏路径不存在或不是文件：<那条已删除的路径>」→ 只有「确定」，点击后保存中止，回到最初的"完全无法保存"状态。
- **原因**：**上一轮修复（问题5 的延迟提交）引入的顺序问题**。清理被推迟到落盘前，于是 `_ApplyGameAutoStart()` 仍在把**用户刚确认删除的**路径喂给 `GameAutoStartManager.ValidateGamePath()`，被判"不存在或不是文件"→ 中止保存。修复前清理在前，自启校验看到的是已清理集合（那时报的是「请先设置至少一个游戏路径」，同样中止，但不会报一条"已被确认删除"的路径）。
- **修复**：①自启校验改为看到"已清理后"的路径视图——临时清空内存取值、跑完自启再还原（事务性不变）；②一条有效路径都没有时**只记录一条 INFO 日志并跳过计划任务创建/删除，开关保持勾选不动**（用户评审时否决了我最初"自动关闭开关"的方案：静默改开关会让用户以为还开着，补回路径后也不会想起重新勾选）；③顺带把"选哪些路径"抽成纯逻辑 `_CollectAutoStartPaths()`（不弹窗），使该分支可脱离 GUI 验证。
- **验证**：脚本实测 9/9 通过——唯一路径失效 + 开着自启时，自启校验看到 0 条路径且不再报错；保存成功、磁盘上路径写空且**开关仍为 1**；补回路径后可正常生成自启任务路径；事务性（中止即还原）保持。
- **连带说明**：计划任务仅由启动时的 `GameAutoStartManager.Reconcile()` 校准（main.ahk），保存流程不做任务校准。故清空路径后**不删除**已存在的旧任务（其触发器指向已删除的 exe，属良性残留），补回路径后由下次 AFA 启动重建。
- [x] 已解决
- [x] 回归验证通过（见「追加测试：问题6 修复后的回归」）

### 问题7：同一次保存里“已清除 N 条失效游戏路径记录”日志出现两次
- **现象**（用户复验问题6 时发现）：一次保存的日志里该条出现两次，中间夹着「无有效路径：跳过随游戏自动启动的计划任务创建」。
- **原因**：`_ClearConfirmedPaths()` 被调用两次——自启校验前临时清空（为了让它看到清理后的视图）、落盘前再清一次——而日志写在 helper 内部，于是每次清空都记一条。
- **修复**：拆开职责——`_ClearConfirmedPaths()` 只清空不记日志，新增 `_LogConfirmedPathsCleared()` 在**落盘成功后**记录一次；同时把日志从落盘前移到落盘后，避免"日志说已清除、实际写入失败"的误导。
- [x] 已解决
- [x] 回归验证通过（用户复验问题6 时确认日志只剩一条）
